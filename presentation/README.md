## 개인 슬라이드 채우는 법

- 왼쪽 세 칸은 **왜 이 작업이 필요했나 → 무엇을 했나 → 다음 개발에 어떻게 쓰이나** 순서로 채운다. 작업 이름만 나열하지 않는다
- 오른쪽 회색 칸에 **실제 작업물 캡처**를 크게 넣는다. 칸 이름이 넣을 것이다 (예: 화면설계서 캡처, WBS 일부)
- 맨 아래 「발표 핵심 한 문장」을 채운다
- 발표자 노트에 안내가 들어 있다. 말할 내용으로 바꿔 쓴다

## 디자인 규칙 (덱 전체가 이렇게 되어 있다)

- 흰 바탕. 표지 · 질문 · 마무리만 남색 면
- **카드 · 그림자 · 동그라미 번호 · 알약 태그 · 블록 화살표를 쓰지 않는다.** 여백, 얇은 회색 가로선(0.75pt), 글자 크기로 나눈다
- 강조색은 파랑 `#4256C8` 하나. 단계 4색(`#7FB2F0` `#F4909F` `#74CDAE` `#F5C46B`)은 「네 칸」을 뜻할 때만 작은 네모로
- 글꼴은 맑은 고딕. 제목 30pt 굵게, 본문 13~16pt, 출처 8.5pt
- 화살표는 글자 `→`

## 말할 때 지킬 것

- 앞부분(아이 · 그림 · 이야기 · 경험)과 뒷부분(설계 · API · AI · Dataset)을 나눈다. 처음부터 기술 이름을 꺼내지 않는다
- **아이를 부족한 존재처럼 말하지 않는다.** 「정상 아동보다 부족」, 「학습능력이 떨어진다」, 「장애를 AI로 개선」, 「창의성을 치료」는 쓰지 않는다
- 대신 「학습 속도와 표현 방식은 아이마다 다르다」, 「글 이외의 표현 방법」, 「참여 기회」, 「창작 경험」으로 말한다
- 연구는 효과를 단정하지 않는다. Narrative Drawing 연구는 아동 1명 사례연구라 「가능성」으로만

## 고칠 때 주의

- **pptx 파일을 직접 고친다.** `tools/deck/build.js` 를 다시 돌리면 손으로 고친 내용이 모두 덮어써진다
- 같은 파일을 여러 명이 동시에 고치면 git 에서 합칠 수 없다 (pptx 는 바이너리). **자기 슬라이드를 고친 뒤 바로 커밋 · push 하고, 시작하기 전에 pull 한다.** 겹치면 한 사람이 받아서 슬라이드를 옮겨 붙인다
- 수치를 바꾸면 [sources.md](sources.md) 에 출처를 같이 적는다
